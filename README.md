# X 回复榜（Chrome 插件）

统计「谁最常在我的 X 帖子下回复我」，给回复者排名，并在时间线和评论区的用户名旁直接标出他的名次和回复次数；榜单里还能看到我在他帖子下回复了几次。数据只存本机，不上传。

当前版本和每版改了什么见 [CHANGELOG.md](CHANGELOG.md)；弹窗标题旁也显示版本号。

需求与决策以《X 入站互动排行插件｜实现规格》（2026-11-13 定版，在 vortex 仓库的 `work/company/业务线/assets/projects/` 下）为底，并按负责人 2026-11-13 的口头调整执行：**只统计回复、只保留回复榜**，引用榜和综合榜不做。

> **当前状态（2026-11-14）**：已在一个真实账号的 Chrome 里运行，读取回复、榜单和时间线标签都能用；逐条核对次数、「我回 N」这条线还没验证过，细项见文末「实测结论」。逻辑和后台流程有自动测试。技术细节和维护约束见 `AGENTS.md`。

## 安装

1. Chrome 打开 `chrome://extensions`，右上角打开「开发者模式」。
2. 点「加载已解压的扩展程序」，选本目录（含 `manifest.json` 的这一层）。
3. 刷新已经打开的 x.com 标签页（装插件之前打开的页面里没有内容脚本）。

改了代码后，在扩展页点刷新按钮，再刷新 x.com 页面。不需要打包，也不上架商店。

## 第一次使用

1. 装好后刷新 x.com，点插件图标，确认弹窗顶部识别出的是你的账号。
2. 设置页「数据读取」里统计范围保持默认的 **7 天**，点「别人回我」那一块的「初始化」。
3. 一两分钟内看弹窗：
   - 显示「进行中：已读 1 页、入库 N 条」→ 接口和解析都对上了，让它继续跑。
   - 显示红色的「解析失败」或「接口返回异常」→ X 的真实返回和代码假设不一致，把这句提示原样交给维护者，不要反复重试。
4. 第一页跑通后，随便打开一条有人评论的自己的帖子，看回复过你 2 次以上的评论者名字旁有没有出现带名次和次数的标签。
5. 抽几个人，对照「通知 → 提及」人工数一下，确认次数对。
6. 都没问题，想看半个月或一个月的，就把统计范围改大，再点一次「初始化」。

## 使用

- **账号**：打开 x.com 后自动识别当前登录的 handle；识别不到时，在弹窗里手动填。数据按账号分开存。
弹窗分「榜单」和「设置」两页。设置页从上到下是：数据读取（统计范围，「别人回我」「我回别人」两份数据各有现状和「初始化」按钮）、榜单口径、标签颜色，最后是默认折叠的「风险说明」和「清空数据」。各处的说明都收在小问号按钮里，点开才显示。

- **统计范围**：7 天（默认）、半个月或一个月，在榜单页或设置页「数据读取」里切换，两处是同一个设置。往回读多远、榜单算多久、时间线标签按哪个榜，都跟着它走。
- **初始化**（设置页「别人回我」）：按统计范围往回读。限速执行，每小时大约能读 4000 多条提及（1000 条约 15 分钟，1 万条约 2.5 小时），范围越大越久，一个月可能要读好几个小时；期间至少留一个 x.com 标签页开着。每次点都是从最新一条重新往回读，已经存过的不会重复计数（所以先跑 7 天、再改成半个月重跑，前 7 天那段会再读一遍，只是多花时间）。遇到限流会自动暂停、退避后续跑；X 的列表翻不到所选范围时，会明说最早拿到哪天。
- **自动增量**：初始化完成之后大约每小时（每次随机隔 50–70 分钟，不卡整点）自动把这段时间新来的读完——从最新往回读，读到上次的位置为止，来了几页就读几页。单次最多读 40 页（约 800 条），超过的部分直接放弃、不提示。同一条回复只计一次；出错中断时下次会重读这一段。只在有 x.com 标签页开着时执行，没有就顺延到下次打开 X。
- **统计口径**：只算**我的帖子下**、别人**直接回复我**的那一条——评论我的帖子，或在我的帖子下回复我的评论。我去别人帖子下评论后对方回我的、引用、普通 @ 提及、回复别人时顺带 @ 到我的，都不算。判断依据是回复所在对话的根帖是不是我发的；个别深层回复在抓取时看不出根帖归属，要等同一对话里有直接评论佐证后才计入。
- **回复榜**：统计范围内按回复次数排，显示名次、头像、名字、@ID、最近一次回复时间、回复次数（次数小块的颜色和时间线标签一致）。可以按名字或 @ID 搜索。**点头像**去他的主页；**点这一行其他地方**在下面展开这个人在范围内回复我的每一条（时间和内容摘要），点其中一条跳到 X 上的原文。右上角的小问号点开是榜单说明，第一条写着范围内一共多少人回复了多少次、上榜多少人。
- **导出**（榜单页）：点「导出」选一种，都是 CSV 表格（Excel 可直接打开）。「导出榜单」是当前榜上的人，一人一行；「导出全量数据」是本机存的每一条回复，一条一行，「别人回我」和「我回别人」在同一张表里用「类型」一列区分，带时间、对方、是否计入榜单、内容摘要和链接。
- **我回 N**：榜单每行在次数小块左边显示「我回 N」——同一统计范围内，**我在他的帖子下**回复了几次（在他帖子下回复别的评论者也算他的；在我自己帖子下回他的不算）。导出的表格里也有这一列。数据读的是我自己主页「回复」栏的列表，每次自动更新后一两分钟跟着读一次；设置页「我回别人」的「初始化」是按统计范围重新读一遍，一次读不完会隔一两分钟自动接着读。不用手动做任何准备：第一次读之前，插件会自己在后台开一个标签页到我主页的「回复」栏，看一眼 X 是怎么请求这个列表的，几秒后自动关掉；X 改版后会自动再来一次。万一没取到，设置页会提示手动打开一次「回复」栏。
- **榜单口径**（设置页）：只有两个条件，都可以用加减按钮调或直接输入。名次上限默认 100，范围 10–500，每次加减 50；最少回复次数默认 2，范围 1–99，每次加减 1。榜单和时间线标签用同一套口径。
- **内联标签**：榜上的人，用户名旁显示「名次 + 回复次数」两个带图标的数字，颜色按回复次数分——看颜色就知道这个人来得多不多；鼠标悬停看最近一次回复时间。标签只读本地快照，不发请求。
- **关系标签**：有帖子的地方（首页、评论区、通知列表等），用户名旁用一个描边的单字标出他和我的关系——「互」互关、「粉」他关注我而我没关注他；其他情况不标。不限于回复过我的人。关系取自 X 页面自己加载这些帖子时带回来的数据，插件不为此多发请求，也不保存，刷新页面后跟着页面重新取。
- **M**（通知列表）：别人回复我的那条如果是在我的帖子下，另有一个单独的「M」；不在我帖子下的不标。先用页面数据判断，判断不了的查本机「别人回我」的数据。
- **时间线上显示什么**（设置页）：名次标签、关系、M 三个开关，各自可开可关；关掉只是不显示，数据照常读。
- **标签颜色**（设置页）：默认 20 次及以上红色，10–19 次橙色，5–9 次蓝色，其余灰色。每一档的次数门槛和颜色都能改，可以加档或删档，最多 5 种颜色；可选红、橙、黄、绿、青、蓝、紫、灰，都是实心底色，X 的白色、暗蓝、纯黑主题下都看得清。下方有效果预览。
- **恢复默认**（设置页）：把名次上限、最少次数和标签颜色一次恢复成默认，不影响数据。
- **自动更新开关**（设置页）：关掉后不再向 X 发任何请求，只展示已有数据。弹窗里的头像图片仍会从 X 的图片 CDN 加载。
- **数据现状与占用**：设置页「数据读取」里两份数据各有一行现状——本机多少条、从哪天到哪天、上次初始化完成的时间和范围、上次更新时间。本机只存每条回复的回复者、时间、所在对话和 100 字以内的内容摘要，一条几百字节；只保留最近 45 天，更早的每天自动清掉。一周一万条回复的量级，长期占用也就二三十 MB。
- **清空数据**：按账号清掉本机的回复数据、游标和任务状态；账号绑定和设置保留。

## 风险提示

后台读取用的是 X 网页版的内部接口，不是官方 API，属于服务条款的灰色地带，可能导致账号被限流。关系标签另外需要在 X 页面里旁听它自己的接口返回（只看不改）。插件只读、低频，不做任何点赞、关注、发帖操作；是否开启由使用者决定，风险自担。数据只存在本机，不上传、不上报。

## 代码结构

| 文件 | 职责 |
|---|---|
| `src/x/fetcher.js` | **抓取层**：在 x.com 页面里用当前会话读一页提及，返回原始 JSON。接口路径、参数、请求头都在这里 |
| `src/x/parser.js` | **解析层**：原始 JSON → 别人对我的回复 + 翻页游标。结构对不上就抛错 |
| `src/content/content.js` | 账号识别、代后台调用抓取层、注入内联标签和关系标签。页面选择器集中在文件顶部的 `SEL` |
| `src/content/tap.js` | 旁听：跑在 X 页面自己的脚本环境里，把页面读接口拿到的返回抄一份转给 `rel.js`。不发请求、不改请求和返回 |
| `src/content/rel.js` | 从旁听到的返回里挑出每个人和我的关注关系、每条帖子的归属，只放在页面内存里 |
| `src/background.js` | 调度：回填任务、增量、限流退避、账号绑定。请求节奏集中在顶部的 `PACE` |
| `src/rank.js` | 统计：时间窗聚合、回复榜、标签快照（纯函数） |
| `src/db.js` | 存储：事件存 IndexedDB（主键 `[账号, 互动 ID]`），状态存 `chrome.storage.local` |
| `src/ui/` | 弹窗界面 |

X 改接口时改 `fetcher.js` 和 `parser.js`；改页面结构时改 `content.js` 的 `SEL`。两种情况插件都会在弹窗里报错或提示，不会静默显示旧数据冒充完整。

请求从 x.com 页面内发出（同源、带会话），所以插件不需要 `cookies` 权限，只申请了 `storage`、`alarms` 和 x.com / twitter.com 的站点权限。代价是后台抓取必须有 x.com 标签页开着。

## 实测结论（规格第 6 节）

2026-11-13 用一个**没有任何提及的小号**测了一轮：接口能通、骨架结构对得上，但因为列表是空的，带真实回复的字段、翻页深度都还没法验证。需要一个有回复的账号再测一轮。

| # | 实测项 | 结论 | 代码里目前的假设 |
|---|---|---|---|
| 1 | 提及列表能往回翻多深 | 未测（小号列表为空） | 不假设深度；翻到底就如实报告最早日期 |
| 2 | 用哪个内部接口、哪些字段标明「回复的是我」 | **部分确认**：`GET /i/api/2/notifications/mentions.json` 返回 200，结构是 `globalObjects` + `timeline.instructions`，游标形态与预期一致；只带公开 Bearer、`x-csrf-token` 等几个头即可，不需要 `x-client-transaction-id`。列表为空时 `globalObjects` 是 `{}`（已按此修正解析层）。**注意**：网页版自己已改用 GraphQL 的 `NotificationsTimeline`（`timeline_type: Mentions`），这个 REST 接口是旧版，随时可能下线，届时要重写抓取层和解析层。回复条目的字段**仍未验证** | 回复看 `in_reply_to_user_id_str` / `in_reply_to_screen_name` 指向我；是否在我的帖子下看 `conversation_id_str`（对话根帖 ID），**该字段是否存在待确认**，缺失时插件会报解析错误 |
| 3 | 用户对象有没有关注状态字段 | 未测 | v1 不使用 |
| 4 | X 数据存档是否含别人对我的回复 | 未测（需负责人自己申请下载存档） | 按「不含」设计 |
| 5 | 安全请求节奏 | **部分确认**：接口响应头显示额度为 180 次 / 15 分钟；当前节奏约 55 次 / 15 分钟。实际回填是否触发风控未测 | 每页间隔 8–15 秒，每 20 页休息 1–2 分钟（约为额度的三成），429 后退避 15 分钟起、逐次翻倍，单次运行 600 页后停下等确认 |
| 7 | 「我回 N」：读我自己的回复列表 | 未测。2026-11-14 写成，接口地址、是否需要额外请求头、返回结构都是按经验假设的；不符时榜单上方会显示读不了或出错 | 照着 X 页面自己发过的请求地址重发，只换用户 ID 和翻页游标 |
| 8 | 关系标签和通知列表的 M：旁听页面数据 | 未测。2026-11-14 写成，用户对象里关注关系的字段名、帖子对象的结构都是按经验假设的；不符时只是不显示标签 | 认 `relationship_perspectives.following / followed_by` 和旧结构里的 `following / followed_by` |
| 6 | 小号先跑一轮回填 | 未做。负责人 2026-11-13 决定直接在主号上用，首次运行按「第一次使用」从 1 周范围开始 | — |
